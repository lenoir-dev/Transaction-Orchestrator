# Transaction Orchestrator specification

## Problem and scope

Treasury, settlement, administration, relaying, payout, and automated contract backends need a durable mapping from a business request to its on-chain outcome. `sign → eth_sendRawTransaction → wait for hash` loses that mapping when a response is lost, a process restarts, a nonce races, a fee becomes insufficient, or a receipt is reorganized. The service owns one logical **Transaction Intent** for each authorized request and records every signed attempt and observation until the result can be established or human reconciliation is required.

V1 targets HTTP EVM JSON-RPC, type-2 EIP-1559 transfers/calls, PostgreSQL ownership and idempotency, a narrow signer boundary, persisted signed bytes, multiple RPC endpoints, bounded replacement, receipt confirmations, shallow reorg recovery, an operational HTTP API, bounded-cardinality telemetry, and a deterministic PostgreSQL/Anvil demonstration.

V1 excludes custody, MPC/KMS implementation, a custom node, private mempool, cross-chain semantics, ERC-4337, arbitrary raw signing, accounting, a full indexer, legacy type-0 transactions, and Kafka/Redis. A KMS/HSM adapter is a later implementation. Contract creation and caller-supplied access lists are excluded initially. The current implementation signs and broadcasts bounded replacement attempts; no production signer or provider is selected.

## Identities and immutable request

An intent has a UUID `intent_id`; within an authenticated tenant scope, `(tenant_id, idempotency_key)` identifies one immutable canonical request. The canonical digest covers caller-supplied chain ID, signer identity, destination, value (wei), calldata bytes, gas profile/explicit limit, and confirmation policy; it excludes JSON whitespace, transport metadata, and the server's policy version. The resolved policy version is stored separately so a later policy update does not turn an identical retry into a conflict. The tenant is derived from authentication, never from a caller's claimed body field. The signer identity selects an allowlisted service account, never a key or arbitrary address. Retry with the same key and digest returns the same intent, including its current state; a different digest returns `IDEMPOTENCY_CONFLICT`. Concurrent requests serialize through a database unique constraint. The key remains retained for the life of the intent and audit retention period; expiry/reuse is not part of v1.

Each intent receives at most one `(chain_id, signer_address, nonce)` reservation; attempts numbered 1..N use that same nonce. The initial attempt has a UUID `attempt_id` and a unique locally derived `transaction_hash` once signed. Different hashes can later represent competing versions of the same intent; a hash is never its business identity. The authorized call fields (chain, signer, destination, value, calldata, gas limit, access list) remain the same for every ordinary replacement. Authorization checks happen before durable creation; the signing component uses the immutable stored policy snapshot and fee ceilings. A changed caller configuration cannot edit a claimed attempt.

## State machine

The schema names `CREATED`, `RESERVED`, `SIGNING`, `READY`, `UNCERTAIN`, `PENDING`, `MINED`, `CONFIRMING`, `CONFIRMED`, `REORGED`, `BLOCKED`, and `FAILED`. `READY` means signed bytes committed; `UNCERTAIN` means submission may have occurred; `PENDING` means provider acceptance or visibility. `MINED` means a receipt matches its block body and the current canonical block at its height. `CONFIRMING` means that inclusion is still canonical but the configured depth is unmet. `CONFIRMED` means that the depth policy is satisfied, with execution outcome reported separately as `SUCCEEDED` or `REVERTED`. `FAILED` remains a proven permanent pre-sign rejection. `REORGED` revokes an invalidated receipt winner and resumes technical reconciliation. A supported reorg can revoke even `CONFIRMED`; a deeper invalidation blocks the intent and degrades readiness. There is no cancellation state or endpoint.

| Transition | Preconditions and atomic persistent write | External effect after commit; retry and crash behavior | Terminal? |
| --- | --- | --- | --- |
| absent → CREATED | Authorized request; insert canonical digest and unique key, or resolve existing row | None; retry returns existing row, crash before commit leaves no row | No |
| CREATED → RESERVED | Locked signer account row; healthy nonce evidence; insert unique reservation and advance next nonce with intent update | RPC reads precede lock; restart resumes reservation; contention retries DB transaction | No |
| RESERVED → SIGNING | Lease/fencing token on intent, immutable unsigned candidate and policy snapshot written | Call signer outside DB transaction; expired lease may be reclaimed; no broadcast before signed bytes commit | No |
| SIGNING → READY | Verify signature, sender, chain, call and nonce; atomically insert signed attempt bytes/hash and state | No RPC; signer timeout returns to recoverable signing when lease expires; crash before commit signs again only without broadcasting either result | No |
| READY → UNCERTAIN | Claim durable broadcast work with lease before network call | Send identical bytes to eligible endpoints; crash/timeout stays uncertain; restart reconciles/rebroadcasts exact bytes | No |
| UNCERTAIN → PENDING | Store endpoint acknowledgment or matching tx/receipt evidence and audit entry | Read-only reconciliation; retry idempotent; crash replays observation | No |
| PENDING → UNCERTAIN | Previously visible hash no longer visible; record observation and deadline | Reconcile all hashes and nonce; absence is not proof; exact-byte rebroadcast allowed | No |
| PENDING/fee-rejected BLOCKED → SIGNING | Due interval, receipt reconciliation permits replacement, bounded fee/count policy and fenced lease | Sign immutable successor outside transaction; an ambiguous transport outcome alone does not permit a new attempt | No |
| signed state → MINED | Receipt hash/index belongs to block body; hash lookup and canonical block number agree; persist evidence and winner atomically | No send; the first observation below the threshold enters MINED | No |
| MINED/CONFIRMING → CONFIRMING | Same receipt block remains canonical; head-based count is below required depth; persist progress | Bounded scheduled polling; restart reads durable evidence | No |
| MINED/CONFIRMING → CONFIRMED | Canonical receipt and `head - receipt_block + 1 >= required`; persist head/hash/depth audit | Execution status remains a separate result, including status 0 | Yes, subject to supported reorg checks |
| MINED/CONFIRMING/CONFIRMED → REORGED/BLOCKED | Canonical block at receipt height has changed; retained window permits rollback / exceeds max depth | Atomically orphan evidence, clear winner/count and audit; deep case pauses account | No |
| REORGED → MINED/PENDING/UNCERTAIN/READY/SIGNING | Reconcile all hashes, canonical blocks and nonce; new receipt / visible signed hash / unknown visibility / existing unsent candidate | Retain intent, nonce and attempts; no immediate fee escalation; unknown nonce consumption blocks | No |
| recoverable → BLOCKED | External nonce conflict, incompatible RPC, exhausted budget, missing raw bytes, or unresolved ownership; record reason | No new signing/broadcast unless safe exact-byte recovery; operator decision required | No |
| BLOCKED → prior recoverable state | Authenticated operator resolves recorded cause, verifies all hashes/chain nonce and policy, clears pause with fenced audit entry | Resume the same intent only; restart sees recorded resume state | No |
| CREATED → FAILED | Proven permanent validation failure before nonce reservation; record reason and audit | No transaction; retry same key returns failed intent | Yes |

`SIGNING` for replacement is distinguished by a pending attempt number; the current signed attempt remains observable. A permanent pre-sign failure after reservation blocks the intent and preserves the nonce for reconciliation. Lease tokens and compare-and-swap updates prevent an expired worker from overwriting a successor. An unsigned candidate may be retried; a signed attempt cannot be edited. Observation writes are idempotent. A replacement is **not** a new intent. Every transition also writes an audit event in the same DB transaction. There is no background transition from uncertainty to a fresh business action.

The implemented signing path claims attempt #1 with immutable gas, fee and policy values, checks signer address, constructs a type-2 transaction, verifies every returned field and recovered sender, then stores canonical signed bytes and locally computed hash in a separate short transaction. A retry of a `READY` intent loads and verifies those bytes. `READY` is durable signed material, not submission or provider acceptance. Broadcast claims `READY → UNCERTAIN` with a fenced lease before RPC. Recovery queries the exact hash and receipt across eligible endpoints before bounded exact-byte rebroadcast. A matching acknowledgment or exact transaction/receipt observation advances to `PENDING`; a fee rejection or conflicting nonce blocks the intent and pauses its account. Replacement creates immutable same-call attempts with explicit lineage, fenced claims and bounded integer fee bumps. Receipt lookup validates block context before stopping sends; `ReconcileReceipts` advances depth policy and revokes invalidated winners.

## Execution boundaries

Create: one short DB transaction inserts or resolves the immutable request. Reserve: the current library uses an explicitly seeded local cursor, then locks `signer_accounts` (`FOR UPDATE`) and records one reservation; production chain nonce reconciliation remains unimplemented. Create signing candidate: one transaction checks policy and lease, allocates attempt number. Call signer outside it. Persist result: one transaction validates fencing token and inserts exact bytes/hash; signed bytes must commit before any network send. Claim broadcast: one transaction marks uncertain and fences ownership; another short transaction records a send slot before RPC. Observation: read RPC outside DB transactions, then commit classified evidence, state, and audit conditional on the lease token. Never hold a DB transaction during signer call, RPC call, or mining. Worker restart scans recoverable leases, `READY`, `UNCERTAIN`, `PENDING`, `MINED`, and `REORGED` rows.

## Safety and operational contract

The signer only signs a fully constructed type-2 transaction bound to configured chain and account. The DB stores exact canonical signed binary and its hash; access to that material and backups must be restricted. Application-level envelope encryption is future work. A transaction hash is computed locally before submission. See [signing architecture](docs/architecture.md), [nonce ownership](docs/adr/0002-nonce-ownership.md), [unknown outcomes](docs/adr/0003-unknown-outcome.md), [replacements](docs/adr/0004-replacement.md), and [RPC trust](docs/adr/0005-rpc-trust.md).

The implemented `BroadcastMetrics` projection groups durable observations by configured endpoint alias, kind, and result. A future exporter uses bounded labels: `txorch_intents_total{result}`, `txorch_attempts_total{result}`, `txorch_pending`, `txorch_unknown_outcomes`, `txorch_replacements_total{reason}`, `txorch_confirmation_seconds`, `txorch_nonce_reservations`, `txorch_rpc_requests_total{endpoint,method,status}`, `txorch_rpc_latency_seconds{endpoint,method}`, `txorch_signer_errors_total{reason}`, `txorch_reorged_receipts_total`. Endpoint labels are configured stable aliases. No hash, intent ID, address, nonce, or request ID in labels. Logs can include IDs with retention and access controls; they never include raw signed bytes, keys, or full calldata by default. Trace attributes follow the same sensitivity policy.

Planned service readiness requires PostgreSQL, configured signer identity, and at least one verified fresh RPC for each enabled chain; liveness only checks the process. Status reports degraded chains and blocked work. Rate limits, tenant quotas, per-signer pending caps and fee ceilings prevent flood and fee exhaustion. The API returns a stable reason code and does not promise exactly-once on-chain execution or inclusion.

## Implemented replacement boundary

`SignReplacement` reads all signed hashes from durable attempt history and checks receipt and transaction lookup on eligible endpoints before a fee decision. A missing result at one endpoint is never treated as proof of absence. It also checks latest account nonce for external consumption. An exclusive account/intent lock creates one `PREPARING` successor and a fenced signing lease. The candidate is rebuilt from the intent and reservation. The same signer validation and immutable raw-byte persistence used for attempt #1 apply. `active_attempt_number` selects the only current attempt; `replaces_attempt_id` links every successor; `winning_attempt_number` is set only by matching receipt evidence. Earlier attempts remain queryable and can win after a later attempt was signed. Receipt presence alone is insufficient: the block and canonical height must match. A canonical inclusion still does not imply absolute finality or execution success.

Eligibility uses the first acceptance/visibility observation for the active `PENDING` attempt, or the first broadcast claim for a fee-rejected `BLOCKED` attempt, plus a caller-supplied minimum interval and clock. A count bound and intent fee ceilings stop escalation with stable `REPLACEMENT_LIMIT_REACHED` and `FEE_CEILING_REACHED` reasons. The configured positive basis-point bump increases both caps to `max(previous + 1, ceil(previous × (10000 + bumpBps) / 10000))`; no ceiling clamping occurs. The implementation has no hard-coded default; tests use 1500 bps and a 120-second interval. A node may reject a candidate as underpriced, so that outcome is audited and another attempt is considered only after reconciliation and the interval. A transport-unknown result does not itself trigger a bump. No network base-fee oracle or guaranteed pool-admission model is implemented.

## Receipt confirmation and reorg boundary

`ReceiptWork` selects at most 1000 due intents, including confirmed inclusions. `ReconcileReceipts` processes at most 8 endpoints and a configured 1–101 attempts serially, with per-call and total read deadlines; no goroutines are started. Its explicit clock and interval persist the next poll on success, absence, or evidence failure. RPC runs outside transactions. Account/intent row locks and an intent version check fence concurrent results. Receipt, winner, count, state and audit changes commit in one short transaction. Inclusion identity is `(transaction_hash, block_number, block_hash)`; immutable receipt rows retain index, status, gas used and effective gas price when supplied. Re-inclusion appends a new observation, including an exact branch return. Verification metadata can progress or mark an observation orphaned; inclusion fields and history cannot be deleted through normal SQL. Minimal receipt/head block evidence retains competing hashes at each height.

Confirmations equal `canonical_head_number - receipt_block_number + 1`. The per-intent depth (1–100000) is resolved from chain policy at creation. Tests use depth 3 and also prove depth 1 with execution status 0. `ReceiptPolicy.MaxReorgDepth` (1–1000) is stored on first poll and must match later calls. The supported window is the larger of the last verified count and the current head distance from the receipt block. Tests use a window of 4: depths 1, 2 and 4 recover; depth 5 enters `BLOCKED/DEEP_REORG_BLOCKED` and `ReceiptReady` fails until operator resynchronization. No nonce reservation is released. A missing receipt with an unchanged canonical block holds the winner; a changed canonical block invalidates it.

An endpoint behind the durable verified head is ineligible for advancement or rollback. A real shorter branch must catch up to that height before this policy can establish a replacement canonical identity. Conflicting eligible canonical block views hold state and return `ErrEvidenceUnavailable`; no votes are counted. One healthy configured endpoint can provide availability, so correlated or malicious RPC remains a trust limitation. The implementation does not use safe/finalized tags, verify consensus proofs, infer wall-clock head freshness, or recover beyond its retained receipt window.
