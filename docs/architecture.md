# Signing and persistence architecture

The persistence library accepts an authenticated intent and an already reserved nonce. The intent owns chain ID, configured signer identity/address, destination, value, calldata, gas limit, and fee ceilings. The first signing claim chooses explicit EIP-1559 fee inputs under those ceilings and writes an immutable `PREPARING` attempt with `attempt_number=1`, a UUID, nonce, gas, both fee values, and policy version. There is no gas estimation or RPC dependency.

`BuildType2` constructs a type-2 transaction from the committed candidate. It rejects negative, zero where disallowed, or over-256-bit quantities; nonce and gas are range-checked before conversion to Ethereum's uint64 fields. Chain ID, destination, value, calldata, gas, fee cap, and tip cap are copied into the transaction. No clock, randomness, network read, or mutable global configuration participates in construction. A later fee change requires another attempt; it cannot edit the current candidate.

`TransactionSigner` exposes only `Address(ctx)` and `SignTransaction(ctx, constructedTx)`. `DevLocalSigner` owns a private copy of an explicitly supplied development key. The expected address from the intent is checked before a signing claim, and the sender recovered from the signed type-2 transaction is checked again afterward. The signed output must match all call and fee fields, including an empty access list. A future custody adapter can implement the same interface without giving application code its key.

The signing flow has two short PostgreSQL transactions separated by the signer call:

1. Lock the intent, create or reclaim the active attempt, set `SIGNING` and a fenced lease, and commit.
2. Call the signer under a bounded context, then validate and encode the signed result outside a database transaction.
3. Lock the intent, verify the lease token and deadline, atomically store raw bytes and locally computed hash, set attempt `SIGNED` and intent `READY`, append audit evidence, and commit.

The first claim persists the exact fee snapshot. An expired claim reuses that row, nonce, call, gas, and fees even if current caller configuration differs. Only a worker with the current lease token can persist a result. Duplicate callers wait within their own deadline for the durable result. A signer timeout releases its claim for retry; malformed output or altered fields blocks the intent and pauses new account allocations with a stable reason code. A configured signer address mismatch blocks before creating an attempt. After correction, explicit resume permits the same attempt to be signed. If recording an error fails, lease expiry still permits recovery. A remote signer may have completed a signature before an application crash; without durable bytes, retrying the same immutable candidate is safe because signing does not submit it to a chain. The remote signer must respect bounded contexts or tolerate duplicate requests for the same candidate.

`READY` means exact signed binary and its hash have committed. It does not mean submitted, accepted, pending, mined, or confirmed. On restart, `LoadSignedAttempt` decodes the stored bytes, recomputes the hash and sender, checks every committed field, and returns a defensive copy. It never re-signs a `READY` intent. The raw bytes are operationally sensitive because anyone holding them could submit the transaction; they are absent from ordinary responses, error strings, metrics, and logs. Restrict PostgreSQL roles and backups accordingly. Application-level envelope encryption and production custody are not implemented.

## Broadcast and reconciliation

`BroadcastEndpoint` isolates JSON-RPC send, transaction/receipt lookup, latest account nonce, chain ID, and optional genesis-anchor reads. `HTTPRPC` is one adapter; callers configure endpoint aliases and URLs. `AdvanceBroadcast` checks endpoint chain identity and read capability before sending. An unavailable primary can be skipped for an eligible fallback. Multiple null responses do not prove absence.

The sender reloads the exact signed attempt and checks its binary/hash before each send. A short transaction changes `READY` to `UNCERTAIN` with the existing fenced lease and writes a claim observation. Another short transaction records one bounded send slot and the chosen endpoint. RPC I/O occurs outside PostgreSQL transactions. A matching returned hash moves to `PENDING`. Timeout, reset, malformed response, or provider error leaves `UNCERTAIN`; a wrong returned hash blocks the intent. An already-known or nonce-too-low error triggers exact-hash reconciliation before it can count as visibility. Fee rejection and evidence of a consumed foreign nonce block the intent and pause further account allocations without changing the signed attempt.

After an uncertain crash or response loss, an expired lease can be reclaimed. The worker checks the exact transaction hash and receipt through eligible endpoints, then checks latest nonce as supporting conflict evidence. An exact transaction or matching receipt moves to `PENDING`; receipt existence is recorded as observation only. If unresolved, a configured maximum send count, duration, and backoff bound identical-byte rebroadcast. On exhaustion, `BLOCKED/OUTCOME_UNRESOLVED` retains the signed bytes and nonce. Replacement uses a separate guarded claim and every historical hash remains observable. The receipt reconciliation service validates canonical blocks, advances confirmation policy and invalidates shallow orphaned inclusions.

`broadcast_observations` and audit events record claim, chosen endpoint, classification, lookup result, and transitions without duplicating raw bytes. `BroadcastMetrics` groups stored observations by bounded endpoint alias, kind, and result; the HTTP `/metrics` handler exports durable and runtime projections. `BroadcastStatus` projects the active hash and separate receipt-winning attempt number/hash without raw bytes; `AttemptHistory` exposes fee and lineage metadata. A block-validated receipt sets a `MINED` winner and stops sends; the confirmation service advances and rechecks it. Production custody and deployment policy remain separate work.

## Replacement claim

`SignReplacement` reconciles every signed hash and latest account nonce before a locked account/intent claim. The claim checks the minimum interval, count, both fee ceilings and the account pause; it commits a successor `PREPARING` row with `replaces_attempt_id`, reason, bump and eligibility time. The signer runs outside the transaction through the common validation path. Expired leases reclaim the same candidate; stale results fail fencing. The broadcast path reloads the active attempt and checks historical receipts again before a replacement send. An old attempt mined at this barrier wins, while the unsent replacement stays in history as `NOT_BROADCAST`. A matching receipt is checked against block hash, height and transaction index before canonical evidence is stored. Confirmation scheduling and reorg recovery use the separate receipt service.

## Receipt reconciliation

`ReceiptWork` selects a bounded due batch, including `CONFIRMED` inclusions, from PostgreSQL. Each caller owns chain configuration and worker concurrency. `ReconcileReceipts` reads all allowed signed attempts serially from up to eight endpoints under per-call and total deadlines. It checks chain ID/optional genesis anchor, the head, receipt identity, block-by-hash body membership, canonical block at the receipt height, and a stable canonical head identity. Peers that can read that height must agree on its hash. A stale head below the durable verified head is ignored; disagreement holds state without voting. Missing receipt evidence does not by itself cause rollback.

After reads, account/intent locks plus an intent version check reject stale work. One transaction writes inclusion/progress, winning attempt, confirmation count, next polling time, minimal receipt/head headers and audit. `MINED` is the first canonical observation below the threshold; a subsequent below-threshold poll enters `CONFIRMING`; threshold satisfaction enters `CONFIRMED`. Execution outcome is independent. Receipt rows preserve immutable inclusion identity and metadata; new branches append observations. A changed canonical hash atomically marks the old observation `ORPHANED`, clears winner/count and enters `REORGED`. The next poll watches all hashes before selecting a new winner or resuming existing signed/candidate work.

The bounded reorg window includes confirmed receipts. Within it, recovery retains intent, reservation and attempt identities. Beyond it, `BLOCKED/DEEP_REORG_BLOCKED` pauses the signer account and `ReceiptReady` reports an incident. Operator resynchronization remains deployment work. Metric projections provide bounded receipt/confirmation/reorg counters, a confirming gauge and fixed confirmation-duration histogram buckets.

## HTTP read and operational boundary

The HTTP server maps configured bearer tokens to tenant scopes and submits through the existing normalization and PostgreSQL idempotency path. New work is admitted only when the configured account, runtime backlog and eligible RPC support progression. A committed retry is read without admitting new work during an outage. The GET projection reads intent, account, attempts, observations and receipts under one read-only repeatable-read snapshot. Raw signed bytes are never selected. Status aggregates chain, endpoint, account and worker state, while readiness reports stable failure reasons. Metrics use fixed classes and configured endpoint names; tracing spans wrap external-effect boundaries. See [operational signals](observability.md) for exact semantics.
