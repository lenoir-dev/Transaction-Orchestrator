# ADR 0007: RPC eligibility, account reconciliation, and bounded runtime

## Decision

An endpoint has a configured ID, chain ID, optional genesis hash, capabilities, and an inflight limit. A bounded probe checks chain identity, anchor, head and canonical block identity, read methods, and both account nonce tags. Wrong chain or anchor makes the endpoint ineligible for the life of the pool. Transient failures enter a timed cooldown; a later successful probe restores eligibility. An endpoint behind the highest healthy observed head by more than `MaxHeadLag` is degraded and excluded from current-state decisions. This lag is an operational freshness threshold, not proof of canonical truth.

The pool caps configured endpoints at eight, global RPC operations at `MaxRPCInflight`, and each endpoint at `MaxInflight`. Endpoint IDs, method names, and a fixed set of result/reason values are the only RPC metric labels. A URL, signer, transaction hash, nonce, and intent ID are never metric labels. Health and latency telemetry stay in memory. Only nonce conflicts that affect correctness enter the durable account reconciliation ledger.

The existing broadcast ledger owns exact raw bytes and the locally computed hash. Eligible endpoints may receive those same bytes under the bounded broadcast policy. A failed endpoint does not authorize a new signature or intent. Reads try eligible providers within the existing deadlines; one null transaction or receipt response does not prove absence. Providers are independent visibility sources, not a voting quorum.

## Network nonce evidence

The [Ethereum execution API](https://ethereum.github.io/execution-apis/api/methods/eth_getTransactionCount/) defines `eth_getTransactionCount` with a block tag. `latest` describes the node's current chain view. `pending` includes the node's pending block view and can differ between nodes. [Transaction lookup](https://ethereum.github.io/execution-apis/api/methods/eth_getTransactionByHash/) and [receipt lookup](https://ethereum.github.io/execution-apis/api/methods/eth_getTransactionReceipt/) can return null. [Block lookup](https://ethereum.github.io/execution-apis/api/methods/eth_getBlockByNumber/) supplies the head and canonical-height evidence used here. `eth_chainId` checks configured chain identity before `eth_sendRawTransaction` is eligible. These RPC methods do not prove global mempool absence or Byzantine canonical truth. `safe` and `finalized` tags are not used by this implementation.

A newly registered network-managed account begins paused and without an initialized nonce. Reconciliation reads `latest` and `pending` from each eligible nonce endpoint. If every successful view agrees, `pending >= latest`, and the pending value fits the local nonce range, the initial `next_nonce` is set to `pending`. An empty or conflicting evidence set leaves allocation blocked. This conservatively avoids reusing a nonce visible in a sampled pending view. It does not prevent an external sender from racing the service after the read.

For an initialized account, the durable `next_nonce` and reservations are never lowered. A network nonce greater than local `next_nonce` blocks the account as an external nonce conflict. Every owned nonce below the observed canonical `latest` must have a canonical confirmed receipt; otherwise the account also blocks. Pending network progression that overlaps an owned reservation with no local send also blocks, even when `pending` equals `next_nonce`. An explainable progression converges without renumbering signed attempts. Disagreeing provider nonces or same-height head hashes leave the account reconciling. A lower provider view cannot reset local ownership. An operator must investigate an external conflict; no automatic skip, reuse, or signed-attempt rewrite is permitted.

Reconciliation first commits a paused account state and a fencing token, performs network reads outside the database transaction, then commits only if its token still owns the account row. A restart can repeat this operation. `ReserveReconciledNonce` reconciles immediately before a new network-managed reservation. The legacy explicit-seed `ProvisionAccount` path remains for the Phase 1 contract and marks its source `TRUSTED_SEED`; deployments should register new operational accounts through `RegisterNetworkAccount` and the reconciled reservation path.

## Runtime and limits

Each runtime start reconciles accounts in bounded keyset pages. It requires account reconciliation after its own startup before it sends or replaces transactions for that account. Receipt reconciliation may continue while an account is paused. Lifecycle work is selected from durable states and retry times in keyset pages, then processed by a fixed worker pool. The worker count must fit below PostgreSQL pool capacity by at least two connections; RPC has separate global and per-endpoint semaphores. One account failure is recorded on that account and does not abort work on another. An intent error gets a durable, capped exponential retry time and class. External calls and workers use bounded contexts; cancellation stops dispatch and joins all workers.

The runtime exposes internal chain endpoint counts/head, endpoint health, account state and blocked-reason counts, reconciliation result counts, active and queued workers, and lifecycle backlog. Account detail, including durable next nonce, is available through `AccountStatus`. It does not expose an HTTP handler in this phase.

## Limits

The service trusts PostgreSQL as its single durable authority and uses RPC observations only within the configured trust policy. Correlated or malicious providers can suppress or falsify evidence. A sample of pending nonces cannot exclude a private transaction or future external signer activity. No provider majority makes a fork canonical. The current startup gate compares a database reconciliation timestamp with the runtime start clock; hosts require synchronized clocks for this freshness test. Deep reorgs retain the Phase 5 fail-closed operator path.
